# ADR-0008 — Вшитый прокси-site + автоприменение конфига на старте

- **Дата:** 2026-09-11 МСК
- **Статус:** Accepted

## Контекст (баг с первым реальным трафиком)

Первый реальный UAG не проксировался и **ничего не появлялось в Decision log**.
Диагностика (radclient + `freeradius -X`) вскрыла два дефекта:

1. **Политики не вызывались.** `apply_config` писал `policy.d/radiuspanel`
   (`radiuspanel_route/srcip/log`), но **виртуальный сервер их не звал** — штатный
   `sites-enabled/default` из образа не патчился и не заменялся. Итог: маршрут по
   правилам не работал, лог не писался. (Не ловили раньше — живого RADIUS не было.)
2. **INSERT лога падал.** `proxy_decision.home_server` был `NOT NULL` без дефолта, а
   `radiuspanel_log` его в INSERT не передаёт → `NOT NULL VIOLATION` → строка не писалась.

Дополнительно: `/etc/freeradius/3.0` **не volume** (в образе), а панель **не применяла
конфиг на старте** → любой ребилд/рестарт backend оставлял FR со старым/stub-конфигом,
пока вручную не нажмёшь Apply.

## Решения

1. **Минимальный прокси-`server default` вшит в образ** (`backend/freeradius/site-default`
   → `sites-enabled/default`): `authorize → radiuspanel_route`, `pre-proxy →
   radiuspanel_srcip`, `post-auth → radiuspanel_log` (+ `Post-Auth-Type REJECT`). Site
   статичен (структура не зависит от конфига), поэтому вшит, а не генерится.
2. **Stub `policy.d/radiuspanel`** вшит в образ (`policy-radiuspanel-stub`), чтобы
   `freeradius -XC` проходил на первом старте (site ссылается на политики). Без SQL —
   валидируется до появления sql-модуля. Панель перезаписывает его на первом apply.
3. **`home_server` (и прочие runtime-колонки) `server_default=''`** — FR-INSERT может
   опускать любые из них без нарушения NOT NULL. Живой БД — `ALTER ... SET DEFAULT ''`
   (нет Alembic; для существующей таблицы create_all не мигрирует).
4. **Автоприменение на старте** (`_apply_on_boot` в lifespan): панель рендерит текущий
   конфиг из БД в FR и перезагружает. Best-effort (не блокирует старт). Делает панель
   самовосстанавливающейся: после ребута/ребилда backend реальные клиенты/правила живут
   без ручного Apply.

## Последствия

- Маршрут по правилам и Decision log работают против реального трафика (проверено
  radclient → запись в `proxy_decision`).
- Ребилд/рестарт backend больше не требует ручного Apply — конфиг восстанавливается сам.
- **Диагностика чужого хоста** (когда UAG не логируется): пакет от неизвестного клиента
  FreeRADIUS дропает молча — на том хосте нужен Client с IP, каким его видит хост
  (учитывать NAT), + Rule. Трейс — `freeradius -X` в backend-контейнере.
- Site — чистый прокси (без локального EAP/PAP); панель не аутентифицирует сама.
