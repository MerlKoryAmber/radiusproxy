# ADR-0012 — Самодиагностика: self-healing watchdog + внутренний health-loop

- **Дата:** 2026-09-22 МСК
- **Статус:** Accepted

## Контекст

Панель — единственная точка на пути RADIUS-аутентификации. Нужно замечать отказы
и, где возможно, чинить их автоматически, иначе — оповещать. Классы отказов
различаются по тому, **кто способен их заметить и починить**:

| Отказ | Кто замечает | Кто чинит |
|-------|--------------|-----------|
| Один таргет недоступен | FreeRADIUS health-check (ADR-0010) | fallback на AD (ADR-0009) |
| Контейнер (backend/db/frontend) упал | только **хост** | рестарт/ребилд — только хост |
| FreeRADIUS-демон умер в контейнере | backend (проверкой) | рестарт контейнера (хост) |
| **Все таргеты пула недоступны** | backend (опрос) | никто — сервисы внешние |
| DC (AD/LDAP) недоступен | backend | никто — внешний |
| Хост/сеть целиком | никто изнутри | внешний мониторинг (вне объёма) |

**Ключевое ограничение:** процесс не может сообщить о собственном падении.
Значит нужны **два независимых механизма** — внешний (переживает падение панели
и умеет чинить) и внутренний (видит прикладные отказы, чинить их рестартом
нельзя).

## Решение

### 1. Внешний watchdog (хост, systemd-таймер, через `rpp`)

Живёт вне docker. Раз в ~1 мин: `docker compose ps` (все ли Up) + `curl -sk
https://localhost/api/health`. При отказе — **лесенка с жёстким пределом** (чтобы
не было петли перезапусков):

1. `compose restart` — до **2 раз** подряд;
2. не помогло → `compose up -d --build` **того же коммита** (без `git pull`) — **1 раз**;
3. не помогло → **стоп авто-действий**, письмо «нужен человек», **cooldown 30 мин**
   (по истечении счётчик сбрасывается и цикл может повториться).

Состояние (счётчики попыток, время последнего действия, текущий инцидент) — в
файле на хосте (`/var/lib/radiusproxy/watchdog.state` или в `ETC_DIR`), **не в
БД** — БД может быть тем, что лежит. Реализация: `cmd_watchdog` в `rpp.sh` +
`ensure_watchdog_timer` (`.service` oneshot + `.timer` OnUnitActiveSec=1min) по
паттерну `ensure_unit`/`ensure_cli` (`common.sh`). Ставится в `install.sh`,
удаляется в `uninstall.sh`.

Письмо на каждом переходе: упал → чиню рестартом → чиню ребилдом → восстановилось
/ сдаюсь. Отправка — тем же SMTP (`MailSettings`, ADR-0011). Watchdog читает
почтовые настройки из БД, если она доступна; если БД лежит — использует локальный
`sendmail`/`mail`, если есть, иначе только пишет в состояние (письмо уйдёт когда
backend поднимется и внутренний loop увидит инцидент). *(деталь реализации — см. код)*

### 2. Внутренний health-loop (backend, рядом с `pool_down_watch`)

Раз в ~30 сек проверяет то, что рестартом не лечится, и пишет **статус
самодиагностики** в БД (для Dashboard-баннера) + письмо на переходах (ok→fail),
дедуп по инциденту:

- **все члены пула недоступны** (внешние сервисы) → баннер + письмо; рестарт
  **не** инициирует (бесполезен);
- **FreeRADIUS-демон не отвечает** (radclient Status-Server на localhost или
  проверка процесса) → баннер + **ставит флаг для watchdog** (это как раз чинится
  рестартом контейнера);
- **DC недоступен** при включённом AD → баннер + письмо (обход 2FA перестанет
  работать).

### 3. Уведомление

- **Письмо** — SMTP из ADR-0011 (переиспользуем `mailer.send_mail`).
- **Dashboard-баннер** — цветной статус здоровья, когда панель открыта (новый
  эндпоинт `/api/system/health` или расширение `/api/dashboard`).

### 4. Тумблер

Settings → авто-восстановление **вкл/выкл** (отдельно от алертов): кто-то захочет
только оповещения без авто-рестарта/ребилда. Хранится в настройках; watchdog
читает флаг перед любым авто-действием.

## Предохранители (обязательные)

- **Предел попыток + cooldown** — рестарт×2 → ребилд×1 → стоп; без этого петля
  сожжёт сервер.
- **Ребилд только текущего коммита**, без `git pull` — авто-ребилд не тянет новый
  код втихую.
- **«Все таргеты недоступны» ≠ поломка панели** — только письмо+баннер, никаких
  рестартов (сервисы внешние).
- **Дедуп писем** — одно на инцидент (как в `pool_down_watch`).
- **Идемпотентность watchdog** — параллельные запуски таймера не должны
  накладываться (flock на state-файле).

## Отвергнуто

- **Авто-`git pull` + ребилд** — авто-обновление кода без человека опасно
  (можно выкатить сломанное в момент аварии). Обновление остаётся `rpp update`.
- **Только внутренняя диагностика** — не увидит падения самого backend.
- **Внешний Prometheus/Alertmanager** — избыточно для одного хоста; watchdog на
  systemd + существующий `rpp`/SMTP достаточно и без новых зависимостей (§16).
- **Бесконечный авто-рестарт** (как `restart: unless-stopped` у compose) — он уже
  есть для штатных падений; watchdog добавляет эскалацию и оповещение, а не
  дублирует его.

## Проверка (план)

- Убить контейнер (`docker kill backend`) → watchdog рестартит, шлёт письма,
  восстановление фиксируется.
- Сломать так, что рестарт не помогает → эскалация до ребилда → до стоп+письмо,
  проверить cooldown и предел (нет петли).
- Погасить все члены пула → баннер + письмо, **без** рестарта контейнеров.
- Убить freeradius-демон внутри → баннер + рестарт контейнера watchdog'ом.
- Тумблер off → только алерты, авто-действий нет.
